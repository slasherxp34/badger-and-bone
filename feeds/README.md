# Shopping feeds

Generated by `build/build.js` on every build — never hand-edited. Both files
read the same `data/products.json` that builds the site, so the price in a
feed and the price on the landing page cannot drift. That matters: price parity
is one of the few Merchant Center violations that suspends an account rather
than just disapproving an item.

| File | Rows | Submit to |
|---|---|---|
| `google-shopping.xml` | 39 items | Google Merchant Center |
| `pinterest-pins.csv` | 53 pins | Pinterest bulk pin creation |

Both feeds carry the **production** origin (`https://badger-and-bone.pages.dev/`) even when built with
`--preview`. A feed is fetched on a schedule for months after submission, so
pointing it at the GitHub Pages preview would have Google crawl the preview and
then fail price parity against the real store.

## Google Merchant Center — free listings

### 1. Publish the two policies Google requires on-site

Free listings ("surfaces across Google") are withheld until the store shows a
real return policy and a real shipping policy at a crawlable URL. Both already
build:

- Return / refund policy: https://badger-and-bone.pages.dev/returns/ and https://badger-and-bone.pages.dev/refund-policy/
- Shipping policy: https://badger-and-bone.pages.dev/shipping/

They must also be entered **again inside Merchant Center**, under
*Settings → Shipping and returns*. Google does not read the on-site pages as a
substitute for the account settings; it checks both and mismatches between them
are a disapproval reason. Enter what the site says:

- Flat US shipping $7.95, free over $65.00
- 30-day returns
- Handling 2–5 business days,
  transit 3–6 business days

### 2. Register the feed

1. Merchant Center → **Products → Feeds → Add product feed**
2. Input method: **Scheduled fetch**
3. File URL: `https://badger-and-bone.pages.dev/feeds/google-shopping.xml`
4. Fetch frequency: daily. The build regenerates the file, so a daily fetch
   keeps Google current with no manual step.
5. Target country **US**, language **en**, currency **USD**

### 3. Verify and claim the site URL

*Settings → Business information → Website*. Verification by HTML file upload
or meta tag; the store is static, so either works. The claimed domain must be
the same origin the feed's `link` values use.

### 4. Attribute notes specific to this feed

**`identifier_exists` is `false` on every item, deliberately.** These are
own-brand products: Badger & Bone is the manufacturer, so no GTIN was ever
issued and there is no third-party MPN. The rule is that an item must carry
either a GTIN/MPN **or** an explicit `identifier_exists: false` — leaving all
three out is an error, and inventing a GTIN is grounds for suspension. Because
`identifier_exists` is false, `brand` becomes mandatory, and it is set.

**Shipping is one `g:shipping` node, not two.** The free-over-$65.00
threshold is *not* expressible as a second 0.00 shipping element — Merchant
Center reads multiple nodes as multiple service options, so a 0.00 node would
advertise free shipping on every order and then mismatch the cart. The feed
therefore declares the flat $7.95 rate in `g:shipping` and tags the item with
`g:shipping_label` = `flat_7.95_free_over_65.00`.
Create the price-based rule ("free over $65.00") in *Settings → Shipping and
returns* and scope it to that label. Account-level rules override feed-level
prices, which is the intended precedence.

**Variants group rather than compete.** Every coat shares
`g:item_group_id` = the product id and differs by `g:color`, so Google shows
one listing with a color switcher instead of six near-duplicates, and
duplicate-content disapprovals do not fire.

**The Day One Kit is included, as a bundle.** Merchant Center does not forbid
bundles — it requires them to be declared. The item carries `g:is_bundle` =
`yes`, one price, and its own id. (A bundle must not carry a component's GTIN,
which is moot here since no item has one.)

### 5. Common disapprovals to expect on first submission

- *Missing return policy* → step 1, the Merchant Center side, not the page.
- *Image too small* → hero renders are 1600×1600; the feed requests the 1200px
  derivative, comfortably over the 250px minimum for non-apparel.
- *Price mismatch* → only possible if the feed is fetched while a build is
  mid-deploy. Fetch daily, deploy atomically.

## Pinterest — bulk pin creation

1. Pinterest **business** account (free), then *Create → Bulk create pins*
2. Upload `pinterest-pins.csv`
3. Confirm the board **"Gifts for dachshund owners"** exists first — the bulk tool fails a row
   whose board it cannot find rather than creating the board.

Column order in the file is exactly what the tool expects
(`Title, Media URL, Pinterest board, Thumbnail, Description, Link, Publish date, Keywords`);
renaming or reordering a column silently drops rows.

- **Publish date is left empty**, which publishes immediately. Fill it
  (`YYYY-MM-DD`) to schedule.
- **Descriptions are keyword-front-loaded and capped at 500 chars.** Pinterest
  weights the opening words of a description for search, so the coat name and
  the product noun lead; brand voice follows.
- **One pin per coat variant** as well as per product, because the coat is the
  search term a dachshund owner actually types ("dapple dachshund gift") and a
  pin showing their own dog's coat is the pin they save.
- **Every link carries UTM** —
  `?utm_source=pinterest&utm_medium=pin&utm_campaign=<slug>_202609&utm_content=feed`,
  plus `utm_term=<coat>` on variant pins — so Pinterest traffic is separable
  from organic in analytics.

### Claim the domain

*Settings → Claimed accounts → Claim a website*. Claiming attributes every pin
that links to the store back to the profile and unlocks pin analytics. It also
makes the store eligible for organic Product Pins, which read the same
Product JSON-LD the PDPs already emit — no extra feed needed.
